Trazabilidad: del requisito al pipeline CI/CD

Objetivo de hoy: leer y construir un diagrama de secuencia UML, y entender la matriz de trazabilidad que conecta cada requisito con su componente, su despliegue y sus pruebas automáticas — el cierre de la cadena completa.

Tu victoria de hoy: sabrás leer un diagrama de secuencia (líneas de vida, activaciones, fragmentos alt/par/opt) y construir la cadena de 4 eslabones: requisito → componente → despliegue → pruebas.

1. El diccionario de esta lección

TérminoDefinición
UMLUnified Modeling Language: notación gráfica estándar (Object Management Group) para modelar software. El diagrama de secuencia es uno de sus tipos.
Diagrama de secuenciamuestra el intercambio de mensajes entre participantes a lo largo del tiempo (arriba = antes, abajo = después).
Línea de vidacaja + línea vertical punteada: un participante (app, gateway, servicio, BD) y su línea temporal.
Activaciónrectángulo fino sobre la línea de vida: el participante está procesando algo en ese tramo.
Mensaje síncronoflecha continua con punta llena: el emisor espera la respuesta antes de seguir.
Mensaje asíncronoflecha con punta abierta: el emisor dispara y sigue (fire-and-forget) — típico de eventos y colas.
Mensaje de retornoflecha discontinua: la respuesta que vuelve al emisor.
Fragmento alt / par / optmarco con etiqueta: alt = alternativas mutuamente excluyentes (cada rama con su guarda [condición]); par = pasos en paralelo; opt = opcional (solo si la guarda se cumple).
Trazabilidadcapacidad de seguir la cadena de un requisito a lo largo de todo el sistema: quién lo implementa, dónde corre y qué lo verifica.
Matriz de trazabilidadtabla con una fila por requisito y columnas: componente que lo implementa, estrategia de despliegue, pruebas que lo verifican.
CI/CDContinuous Integration / Continuous Delivery: integración continua (cada cambio se compila y prueba automáticamente) y entrega/despliegue continuo (el código verificado sale a producción de forma automatizada).
Pipelinela «tubería» automatizada del CI/CD: build → pruebas unitarias → BDD/Gherkin → carga → despliegue.
k6herramienta open source de pruebas de carga: ejecuta scripts que simulan miles de usuarios/peticiones y verifica umbrales (p99, throughput).
Prueba de caosinyectar fallos deliberadamente (matar un nodo, cortar la red) y comprobar que el sistema se recupera según lo especificado.
Prueba de spikeprueba de carga con un pico abrupto: verifica el comportamiento del auto-escalado ante ráfagas.
Kubernetes (K8s)orquestador de contenedores: gestiona réplicas, reinicios y despliegues sin downtime.
HPAHorizontal Pod Autoscaler (Kubernetes): añade o quita réplicas automáticamente según métricas (CPU, longitud de cola).
PodDisruptionBudgetregla de Kubernetes: cuántas réplicas deben seguir vivas durante mantenimientos — protege la disponibilidad.
WAFWeb Application Firewall: cortafuegos de aplicación que filtra tráfico malicioso en el borde de la red.
JWTJSON Web Token: token firmado que acredita identidad y permisos (el «pase» del repartidor en cada petición).
HMACHash-based Message Authentication Code: firma de mensajes con clave compartida — demuestra que el mensaje no fue alterado ni falsificado.
Rate limitinglimitar la tasa de peticiones por cliente: protege contra abuso y ataques de denegación.
Mermaid / PlantUMLlenguajes de texto→diagrama: escribes la secuencia como texto y la herramienta genera el diagrama — ideal para repos y entregas.

2. Leer un diagrama de secuencia: la secuencia de asignación

La secuencia típica del Caso C — verla con el diagrama SVG completo en el cheat sheet de trazabilidad y UML:

  1. App repartidor → API Gateway: PATCH de posición (con JWT). Mensaje asíncrono: la telemetría no espera respuesta.
  2. API Gateway → Motor de matching: verifica token + rate limit.
  3. Motor → Redis Geo: GEOADD actualiza el índice; ACK en ~10 ms (retorno discontinuo).
  4. Marketplace → Motor: POST /ordenes (mensaje síncrono: el cliente espera).
  5. Fragmento alt: [lock SETNX R-77 OK] → asigna y escribe en PostgreSQL (transacción) → devuelve 201 en p99 ≤ 200 ms · [lock falla] → 409 y la orden reempareja.

El paso 5 es la condición de carrera de la Lección 3 convertida en notación gráfica: el alt es el Entonces del escenario Gherkin, el lock es la decisión del ADR, y «p99 ≤ 200 ms» es la medida del RQ-01. Una sola historia contada en cuatro documentos — eso es trazabilidad.

RQ-02 disp. ≥ 99,95% · RTO ≤ 30 sclúster Redis + Kafka buffermulti-zona, sin downtimecaos (matar nodo) + Gherkin @fallo-critico
RQ-03 ≥ 99,9% falsificados rechazadosAPI Gateway (JWT + rate limit)WAF en el bordetests de seguridad + Gherkin @seguridad
RQ-04 ×3 en ≤ 60 sKafka particionada + consumidores sin estadoauto-escalado horizontalspike test k6 + verificación HPA
La regla de oro de la trazabilidadNo dejes ningún eslabón vacío. Requisito sin prueba automática = opinión; componente sin requisito = sobre-ingeniería. Y la métrica del test debe ser idéntica a la medida de respuesta del Módulo 1: «p99 ≤ 200 ms» aparece en los dos sitios, palabra por palabra.
