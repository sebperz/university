Calidad y requisitos

TérminoDefinición operativa
Atributo de calidadPropiedad medible del sistema que no es funcionalidad (p. ej., latencia, disponibilidad). Responde a «qué bien lo hace», no a «qué hace».
Requisito funcionalLo que el sistema debe hacer: asignar una orden a un repartidor.
Requisito de atributo de calidadCómo debe hacerlo: en ≤ 200 ms (p99), aun con 40.000 repartidores conectados.
Adjetivo abstractoPalabra sin métrica («rápido», «robusto», «escalable», «seguro»). Prohibida en la matriz del Módulo 1: toda afirmación debe llevar número, umbral y condición.
Trade-offIntercambio inevitable entre atributos (más seguridad ⇒ más latencia). Los ADR documentan qué trade-off se eligió y por qué.
SLA / SLOObjetivo de servicio medible (SLO) y su compromiso contractual (SLA), p. ej. disponibilidad mensual ≥ 99,95%.
Percentil p99Valor bajo el cual cae el 99% de las mediciones. «p99 ≤ 200 ms» tolera que 1 de cada 100 peticiones sea más lenta.

PartePregunta que responde
Fuente del estímulo¿De dónde viene? (usuario, servicio externo, nodo interno, atacante)
Estímulo¿Qué evento llega al sistema?
Artefacto¿Qué parte se ve afectada? (motor de matching, cola, BD…)
Entorno¿Bajo qué condiciones? (operación normal, sobrecarga, caída parcial)

Gherkin / BDD

TérminoDefinición operativa
BDDDesarrollo guiado por comportamiento: los criterios de aceptación son ejemplos concretos ejecutables.
GherkinDSL de Cucumber para escribir esos ejemplos. Localizable con # language: es.
Dado (Given)Estado inicial del sistema (precondición). Sin interacciones del usuario.
Cuando (When)El evento o acción que se especifica (uno por escenario).
Entonces (Then)Resultado esperado observable (salida del sistema), no estado interno oculto.
Y / Pero (And/But)Encadenan pasos del mismo tipo para legibilidad.
Scenario Outline / ExamplesPlantilla paramétrica (<param>) ejecutada una vez por fila de la tabla Examples.

Fuente: Fowler — GivenWhenThen; Cucumber — Gherkin Reference. Detalle: referencia Gherkin.

ADR (Architecture Decision Record)

TérminoDefinición operativa
ADRDocumento corto e inmutable que captura una decisión arquitectónica: contexto, decisión, consecuencias.
Ciclo de vidaProposed → Accepted (o Rejected); si cambia el criterio, un ADR nuevo supersedes al anterior, que no se edita.
Two-way doorDecisión reversible y barata de cambiar: AWS recomienda decidir rápido en vez de discutir sin fin.
Decisión arquitectónicamente significativaAfecta estructura (microservicios), requisitos no funcionales, dependencias, interfaces o técnicas de construcción.

Fuente: AWS Blog — Master ADRs; AWS Prescriptive Guidance — proceso. Plantilla: plantilla ADR AWS.

Sistemas distribuidos (contexto del Caso C)

TérminoDefinición operativa
Teorema CAPAnte una partición de red, un nodo debe elegir entre consistencia (C) o disponibilidad (A); P es obligatorio en sistemas distribuidos.
Consistencia fuerteToda lectura devuelve la última escritura: los nodos se coordinan antes de responder (CP).
Consistencia eventualLas réplicas convergen si no llegan nuevas escrituras: se responde rápido y se reconcilia después (AP).
Condición de carreraDos operaciones simultáneas compiten por el mismo recurso y el resultado depende del orden de ejecución (p. ej., doble asignación de un repartidor).
Bloqueo / lockPrimitiva que garantiza que una sola entidad ejecute la operación crítica (setnx con TTL, fila atómica).
IdempotenciaRepetir la misma operación produce el mismo efecto que ejecutarla una vez (clave de idempotencia en el mensaje).
Cola / brokerMensajería asíncrona (p. ej., Kafka) que desacopla productores y consumidores y amortigua picos.
API GatewayPunto de entrada único: autenticación, rate limiting, enrutamiento.
BackpressureMecanismo para no saturar: si el consumidor va lento, se retiene/rechaza carga en vez de colapsar.
Circuit breakerInterruptor que corta llamadas a un servicio caído y permite degradación controlada con reintento periódico.
Escalado horizontalAñadir réplicas (más instancias) en vez de máquinas más grandes; requiere estado compartido o particionado.

Verificación y CI/CD

TérminoDefinición operativa
Prueba de cargaReproduce el pico esperado (p. ej., k6 con 2.000 órdenes/min) y mide p99/throughput contra la medida de respuesta.
Prueba de caosInyecta fallos (matan un nodo) y verifica el escenario Gherkin de recuperación.
Pipeline CI/CDSecuencia automatizada: build → pruebas unitarias → BDD/Gherkin → carga → despliegue.
Matriz de trazabilidadTabla que conecta cada requisito con el componente que lo implementa y las pruebas que lo verifican.
Diagrama de secuencia UMLMuestra el intercambio de mensajes en el tiempo entre participantes (líneas de vida, activaciones, alt/par).
