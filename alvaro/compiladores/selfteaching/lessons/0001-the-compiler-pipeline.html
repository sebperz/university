Lesson 1

The Compiler Pipeline

First map, then move. 15 minutes · ties to course "Actividad 1" · glossary

Before writing any code, you need the map. A compiler is not one magic program — it is a pipeline of small phases, each transforming the program into a form the next phase can work with. Every phase in this course and every brick of our Python interpreter is one of these stages. Learn the map once and every later lesson is just "we're building stage N."

The map

characters → tokens↓

The four stages are split into two groups. The first three are the front end — they only care about the source language and look the same for every compiler. The last is the back end — it cares about what you're compiling to.

Stage 1 — Lexical analysis (análisis léxico)

The lexer reads characters one by one and groups them into tokens. It answers "what are these words?" The text 1 + 22 becomes the tokens NUMBER("1"), PLUS("+"), NUMBER("22"). Note the two-part structure: a token type (what kind of thing it is) and a lexeme (the actual characters). This is also where regular expressions and DFAs from your course live.

Stage 2 — Syntax analysis / parsing (análisis sintáctico)

The parser checks that the sequence of tokens follows the grammar. It answers "is this the right shape?" It produces a tree of the program's structure — the AST. This is where grammars, productions, and ambiguity from your course live.

Stage 3 — Semantic analysis (análisis semántico)

The semantic analyzer checks meaning: types, declared names, legal operations. Shape can be perfect while meaning is broken. This is where symbol tables and type checking live.

The distinction your course will test

Syntax checks the form; semantics checks the meaning. From your "Actividad 1": let x = (5 + 3; is a syntax error (shape is wrong — an unclosed parenthesis), while let x: i32 = "hola"; is a semantic error (shape is fine, but the types clash).

Stage 4 — Evaluator / code generation (generación de código)

Finally the program actually runs or becomes machine code. Interpreters evaluate the AST directly; compilers emit a target program. Our project starts as an interpreter — simpler, and the concepts carry over.

Why this matters for our project

We will build the interpreter in this exact order, mirroring Crafting Interpreters, the best project-based book on this topic. Each lesson adds exactly one stage to our Python project. Today you build the first brick: a lexer.

Exercise 1 · the lexer

Create a folder for the project (inside this workspace, e.g. ./project/) and save this file as lexer.py. Then run it with python3 lexer.py:

TOKEN_TYPES = ("NUMBER", "PLUS", "MINUS", "STAR", "SLASH", "LPAREN", "RPAREN", "EOF")

class Token:
    def __init__(self, type_, lexeme):
        self.type = type_
        self.lexeme = lexeme
    def __repr__(self):
        return f"Token({self.type}, {self.lexeme!r})"

class Lexer:
    def __init__(self, source):
        self.source = source
        self.pos = 0

    def make_token(self, type_, lexeme):
        if type_ not in TOKEN_TYPES:
            raise SyntaxError(f"Unknown token type {type_!r}")
        return Token(type_, lexeme)

    def next_token(self):
        while self.pos < len(self.source) and self.source[self.pos].isspace():
            self.pos += 1
        if self.pos >= len(self.source):
            return self.make_token("EOF", "")
        c = self.source[self.pos]
        if c.isdigit():
            start = self.pos
            while self.pos < len(self.source) and self.source[self.pos].isdigit():
                self.pos += 1
            return self.make_token("NUMBER", self.source[start:self.pos])
        symbols = {"+": "PLUS", "-": "MINUS", "*": "STAR", "/": "SLASH",
                   "(": "LPAREN", ")": "RPAREN"}
        if c in symbols:
            self.pos += 1
            return self.make_token(symbols[c], c)
        raise SyntaxError(f"Unexpected character {c!r} at position {self.pos}")

    def tokenize(self):
        tokens = []
        while True:
            t = self.next_token()
            tokens.append(t)
            if t.type == "EOF":
                return tokens

for t in Lexer("1 + 22 * (3 - 4)").tokenize():
    print(t)

Your win for today: you should see eight real tokens followed by Token(EOF, ''). Notice how 22 became one NUMBER token, not two — that's the lexeme grouping working.

Then modify: add ";": "SEMICOLON" to the symbols dictionary and a ; to the test string. Then add "SEMICOLON" to symbols but don't add "SEMICOLON" to TOKEN_TYPES — run it. You should get SyntaxError: Unknown token type 'SEMICOLON'.

Why does that error make sense? TOKEN_TYPES is the fixed vocabulary of the whole pipeline — the parser (next lesson) switches on exactly these strings to build the tree. If the lexer could mint new token types at runtime without declaring them, it would silently break the parser later. Real compilers enforce this with an enum. That is why token types exist.

If you tried this before and saw no error, that's because the first version of this exercise never actually checked TOKEN_TYPES — it was dead code. The make_token method above fixes that, and is a genuine design improvement for the project.
